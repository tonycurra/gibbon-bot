HAT

Waveshare Bus Servo Driver HAT (A) + ST servos. USB feeds the ESP32. XT60 feeds the motors. Every sensor byte is a READ of the servo’s own table — not a HAT IMU. Gold dumps from this board sit at the bottom. Low-level hand poke: /raw/.

1. how fast is the bus

50 ms is comfortable, not the ceiling. The wire is 1 Mbps. Firmware will not stream faster than 40 ms (stream N). That is ~25 Hz on the ID you care about. The servo’s position PID inside the case is kHz. BLE to a phone in an olive grove should be 1–5 Hz, not this bus.

2. inside the servo chip

Not just an encoder. Each ST is a closed-loop joint: ARM-class MCU, 12-bit digital magnetic encoder (0–4095), MOSFET driver, DC motor + gears, EEPROM. We cannot flash that MCU. We cannot PWM the phases. Analog in the case is VIN and a current estimate — both digitized before they hit the bus.

External force today = load (and maybe cur) while torque is on. Backdrive with tq=0 is blind to strain. Impedance control is not in the vendor loop — later, if ever, as a host layer on load, not Ohm’s law on the winding.

3. ways to command — you do not pick the spline

Yes: you say “go to this angle from here.” The servo MCU does one shape: goal position, a speed cap, and an acceleration byte. That is a trapezoid-ish ramp inside the servo. There is no cubic, no S-curve table, no host polynomial. Time register 44 exists; we write 0.

Default path (keep it): mode 0, tell it position + speed (default 300) + acc (default 20). The PID is already running. A second PID on the ESP32 that outputs position fights that one. Faster / slower = speed. Softer start = acc. Softer push later = max-torque @16 (not wired). Do not retune Kp/Kd/Ki first. Do not open-loop PWM the motor from here — not worth it, and we cannot reach the phases anyway.

Many small to hops from the ESP32 (trapezoid on our side) is the only extra curve we can add without touching EEPROM. Leave the vendor loop on. Supervise from the ESP32: walls, VIN, load-cut, unwrap.

4. unwrap — not wheel. “put it back to 0”

Wheel on 16, put it back to 0 meant: after a speed-jog, write register 33 = 0 (servo mode) so the next boot is not still spinning. It did not mean drive the horn to encoder zero. Wheel mode is EEPROM — it survives power-off. That is the hazard.

Your counter idea is already the right one, and it does not need wheel mode. Encoder works in servo and in wheel. Firmware unwrap_pos():

if Δpos > +2048 → turns −1
if Δpos < −2048 → turns +1
un = pos + turns × 4096

If counts go up, un goes up. If they go down, down. Crossing 0/4095 is just a ±1 turn. Same code for every ID. Walls live in un (or Δ from a slack here), not in raw 0–4095.

Wheel was only a way to command through the seam because WritePos is linear and stops at 0/4095. Stay in servo. Walk hops that do not cross the seam, or send a goal on this side of 0. Wrist roll (16) and shoulder yaw (11) wrap. Shoulder pitch 12+13 is a limited arc (two motors, opposite counts) — magnet wrap is not that joint’s usual problem.

Do not switch 16 to wheel for range. 2026-09-05: bus died, wheel kept pushing, cable wound. Servo mode + unwrap + hop limits is the agnostic path.

6. plan of attack

  1. Leave vendor PID. Command pos + speed + acc. Flash ESTOP / raise SyncWrite already in the tree.
  2. Unwrap + hop for wrap joints (11, 16). No wheel for range.
  3. Sensitivity = load trip (console slider → guard hand N / estop / free). Chip must own the cut. Phone/console is backup.
  4. Energy later: EMA of V and |I| + mWh on the 40–80 ms tick. Not impedance. Not ms BLE.
  5. Grove radio: 1–5 Hz pose/energy; estop immediate. Inner loop stays in the servo.

Worth low-level electric control of the motor? No on this hardware. Worth a raw sitting on the hand to feel speed/acc/load? Yes — next section.

7. raw hand test

Hand only: open / close / hold / free, grip slider, STOP if effort (servo load counts) goes past the bar. Live graphs of pos, effort, mA, V, °C. Bus hex is behind “servo dump”. open /raw/. Pack on. Support the jaws. STOP / Escape still kills torque.
